# 화살 섹터 브로드캐스트 & 동기화 구조 정리

## 최종 구조 요약

화살은 수명이 짧고 직선 이동하는 결정론적 객체이므로,
일반 객체(플레이어/몬스터)와 다른 단순한 생애주기 관리를 채택한다.

```
[생성]  서버 Arrow::UpdateIdle() (_ifSpawned)
         → BroadcastBySector(S_AddObject, 스폰 위치 기준 3×3)
         → InsertAtSector로 섹터 컨테이너 등록
         → 클라: 수신 즉시 같은 초기 대기 시간 적용 후 이동 시작

[이동 중] 매 타일 이동마다
         → BroadcastMoveBySector(S_Move) — 클라 위치 보정용
         → InsertAtSector로 _sectorArrows 갱신
         → 섹터 경계 넘을 때: DoSomethingCrossingSectors로 경계 플레이어에게 S_AddObject / S_RemoveObject

[플레이어 섹터 이동 시] Handle_C_Move
         → 플레이어/몬스터: delta 3섹터 방식 (DoSomethingCrossingSectors)
         → 화살: 새 시야 범위 9섹터 전수 스캔
             add: 새 3×3 내 모든 _sectorArrows → S_BROADCAST addobjects
             remove: 구 3×3에만 있던 섹터의 _sectorArrows → S_BROADCAST removeobjects

[소멸]  벽 충돌 or 타이머
         → BroadcastBySector(S_RemoveObject, 소멸 위치 기준 3×3)
         → DeleteProjectiles()에서 Leave() → DeleteFromSector
```

---

## 버그 원인 분석

### Bug 1: InsertAtSector 미호출

**증상:** 화살이 섹터를 이동해도 `_sectorArrows` 컨테이너가 갱신되지 않음.
스폰 위치 섹터에 화살이 영구 등록된 상태로 남음.

**원인:** `Arrow::UpdateIdle()`에서 `SetCellPos(nextPos)` 후 `InsertAtSector`를 호출하지 않음.
- `_ifSpawned` 경로: 첫 이동 후 S_AddObject만 보내고 섹터 갱신 없음
- 섹터 경계 이동 경로: `DoSomethingCrossingSectors`로 알림만 보내고 섹터 갱신 없음

**수정:** `SetCellPos(nextPos)` 직후 항상 `InsertAtSector` 호출.
같은 섹터면 early return이라 비용 없음.

---

### Bug 2: 동일 틱 내 순서 경쟁

**증상:** 플레이어가 섹터를 왔다갔다 할 때 화살이 간헐적으로 안 보임.

**원인:** 메인 스레드 한 틱 안에서 순서가 고정되어 있음.

```
FlushJobs()  → C_Move 처리 (플레이어 섹터 이동) → 이 시점 화살 위치 기준으로 delta 3섹터 체크
Update()     → Arrow::UpdateIdle() (화살 섹터 이동) → 이 시점 플레이어 위치 기준으로 알림
```

**재현 시나리오:**
```
화살: 섹터 (2,3) → 이번 틱에 (1,3)으로 이동 예정
플레이어: 섹터 (3,3) → (2,3)으로 이동

[FlushJobs] 플레이어 이동 처리:
  delta add 대상 = 섹터 (1,x)
  화살은 아직 (2,3) → add 대상 아님 → 플레이어에게 화살 S_AddObject 미전송

[Update] 화살 이동:
  delta remove 대상 = 섹터 (3,x)
  플레이어는 이미 (2,3) → remove 대상 아님 → 제거 패킷도 미전송

결과: 플레이어 (2,3), 화살 (1,3) → 시야 범위 내인데 클라에서 화살 없음
```

**수정:** 플레이어 섹터 이동 시 화살에 한해 delta 방식 대신 **새 시야 범위 9섹터 전수 스캔**으로 전환.
타이밍과 무관하게 현재 `_sectorArrows` 상태를 기준으로 가시성을 결정.

---

### Bug 3: 클라 Handle_S_BROADCAST 화살 케이스 누락

**증상:** 서버가 S_BROADCAST에 화살 정보를 담아 보내도 클라에서 무시됨.

**원인:** `Handle_S_BROADCAST`의 addobjects 처리 루프에
`OBJECT_TYPE_PROJECTILE` else if 케이스가 없었음.

화살의 주 알림 경로가 `S_AddObject` 직접 전송이라 대부분의 경우 동작하고 있었고,
"플레이어 섹터 이동 시 이미 그 섹터에 화살이 있는 경우"만 누락되어 증상이 간헐적으로만 나타남.

**수정:** `Handle_S_BROADCAST` addobjects 루프에 `OBJECT_TYPE_PROJECTILE` 케이스 추가.
`GetGameObject(id) == nullptr` 중복 체크로 이미 알고 있는 화살은 재생성 안 함.

---

### Bug 4 (근본 원인): 서버-클라 화살 초기 위치 1타일 오프셋

**증상:** 충돌 연출이 시각적으로 1타일 밀려 보임. 클라 화살이 항상 서버보다 1타일 앞서 있음.
데드 레커닝으로 어떻게 보정해도 충돌 타이밍이 맞지 않음.

**원인:** 서버와 클라의 화살 초기 이동 시작 시점이 다름.

```
서버: 스폰(플레이어 위치) → _waitUntil 세팅 → 1타일 대기 → 첫 이동
클라: 스폰(플레이어 위치) → 즉시 이동 시작

→ 클라가 서버보다 항상 1타일 앞선 위치를 렌더링
→ 서버가 타일 N에서 충돌 감지 시 클라는 이미 타일 N+1 진입
```

**수정:** 클라에서도 서버의 초기 `_waitUntil`과 동일한 대기 시간을 적용한 뒤 이동 시작.
S_AddObject 수신 시 `waitUntil = now + (48 / movespeed) * 1000` 설정 후 이동 시작.

**이것이 오늘 다룬 모든 시각 오차의 근본 원인이었음.**
충돌 보정, TIP 예측 등 여러 접근을 시도했으나, 결국 이 1타일 오프셋을 수정하자
데드 레커닝만으로 매 틱 broadcast와 동일한 정밀도가 나왔음.

---

## 데드 레커닝 vs 매 틱 Broadcast 트레이드오프

### 최종 채택: 매 타일 BroadcastMoveBySector + 데드 레커닝 병행

매 틱 broadcast를 복구한 뒤, 초기 오프셋 수정으로 데드 레커닝의 정밀도도 확보.
결과적으로 두 방식이 동일한 연출을 내게 됨.

| | 매 틱 Broadcast만 | 순수 데드 레커닝 | 현재 (병행) |
|---|---|---|---|
| 패킷 수 | 화살 수 × 타일 수 × 근처 플레이어 수 | 생성 1회 + 소멸 1회 | 매 타일 S_Move (보정용) |
| 위치 정밀도 | 항상 정확 | 오프셋 수정 후 정확 | 항상 정확 |
| 네트워크 오차 복구 | S_Move로 즉시 보정 | 불가 (드리프트 누적) | S_Move로 보정 가능 |
| 충돌 연출 정밀도 | 정확 | 오프셋 수정 후 정확 | 정확 |
| 구현 복잡도 | 낮음 | 높음 (오프셋 관리) | 중간 |

### 성능 관점

화살에서 매 타일 S_Move를 보내는 실제 비용:

```
화살 1개의 최대 이동 타일 수 ≈ 맵 가로 63타일
근처 플레이어 수 ≈ 최대 수십 명 (현재 규모에서 수 명)
화살 동시 존재 수 ≈ 플레이어 수 × 공격 빈도

→ 매 틱 전체 broadcast에 비해 BroadcastBySector로 근처만 전송
→ 화살 수명이 짧아 총 전송량 자체가 작음
→ 현재 게임 규모에서 무시할 수 있는 수준
```

### 데드 레커닝이 주는 실질적 이점

매 타일 S_Move를 보내면서도 데드 레커닝을 유지하는 이점:

1. **네트워크 지연 완화:** S_Move 패킷 사이에 클라가 자연스럽게 보간 — 끊김 없는 화살 이동 연출
2. **패킷 손실 내성:** S_Move 1~2개가 유실되어도 클라가 방향/속도로 위치를 추정해 버팀
3. **서버 부하 분산:** 클라가 중간 위치 계산을 담당 — 서버는 타일 단위 판정에만 집중
4. **확장성:** 화살 수가 늘어나도 클라 렌더링은 자체 계산으로 처리

## 섹터 관리 트레이드오프

### 화살을 섹터 컨테이너로 관리

| | 섹터 관리 O (현재) | 섹터 관리 X (전역 리스트) |
|---|---|---|
| 플레이어 이동 시 화살 탐색 비용 | O(9섹터 내 화살 수) | O(전체 화살 수) |
| 화살 이동 시 갱신 비용 | InsertAtSector O(1) | 없음 |
| 구현 복잡도 | 높음 | 낮음 |
| 맵이 커질수록 | 유리 | 불리 |

### 화살에 9섹터 전수 스캔을 쓰는 이유

플레이어/몬스터는 delta 3섹터 방식으로 충분하지만, 화살은 매 틱 이동하는 고빈도 객체라
FlushJobs(플레이어 이동) → Update(화살 이동) 순서 경쟁에서 delta 방식이 누락을 만들어냄.

**허용 가능한 이유:**
- 화살 수가 적고 수명이 짧아 전수 스캔 비용이 미미함
- 플레이어 섹터 이동 빈도 자체가 높지 않음 (타일 단위 이산 이동)

## 충돌 연출 설계 결론

### 클라 렌더링 예측 (정적 벽)

```
클라: tilemap.IsWall(nextTile) == true → 렌더링 OFF (시각 예측)
서버: S_RemoveObject → 실제 오브젝트 제거 (판정 권위자)
```

- **정적 벽:** 클라 예측과 서버 판정이 항상 일치 → 완벽한 연출
- **동적 오브젝트(몬스터/플레이어):** 클라 예측을 쓰지 않고 서버 S_RemoveObject를 기다림
  - 이유: 몬스터가 이동하면 클라 예측이 틀려 화살이 깜빡이는 현상 발생

### 판정과 연출의 분리 원칙

| 역할 | 담당 | 근거 |
|------|------|------|
| 시각적 위치 | 클라 데드 레커닝 | 부드러운 이동 연출 |
| 벽 충돌 연출 | 클라 tilemap 예측 | 정적 데이터라 항상 정확 |
| 실제 충돌 판정 | 서버 | 치트 방지, 권위자 |
| 오브젝트 제거 | 서버 S_RemoveObject | 모든 클라 동기화 |

## 미해결 잠재 이슈

### 화살 소멸 S_RemoveObject 범위

소멸 패킷이 소멸 위치 기준 3×3만 커버함.
화살 생성 시 알게 된 플레이어가 소멸 위치 범위 밖으로 이동했으면 제거 패킷을 못 받음.

**완화책:**
- 클라 화살에 최대 비행 타이머를 두어 서버 확인 없이 자체 제거
- 또는 소멸 시 `Broadcast` (전체 전송) — 소멸은 드문 이벤트라 부하 미미

### 고속 플레이어 화살 터널링

플레이어 이동속도 > 화살 이동속도인 경우, 같은 틱에 서로 교차해도 동일 타일을 점유한 순간이 없어 충돌 미감지.

**현재 결정:** 빠른 플레이어가 느린 화살을 피할 수 있다는 것을 게임플레이 요소로 허용.
수정 시 경로 스윕 체크가 필요해 복잡도 대비 효과가 낮음.
